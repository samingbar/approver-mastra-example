`npm run demo:capacity` reads the existing local system and writes `.data/demo-results/capacity-latest.json`. It reports approximate Temporal queue backlog count/age, task arrival/dispatch rates, recent activity schedule-to-start p95, observed active activities/retries/provider throttling, PostgreSQL review queue age, and Docker CPU/memory use. It never creates infrastructure or changes replicas by default.

`npm run demo:capacity -- --watch` repeats observations every 30 seconds. Queue age above 15 seconds or schedule-to-start p95 above 5 seconds must persist for two observations before proposing growth. Shrinking requires three empty observations with zero observed active activities and latency below one second. Replica bounds are one through three per worker service. Missing queue, replica, or fixed-resource observations hold capacity. Older history samples can delay shrinking; this is a conservative teaching tool rather than a production controller.

Add `--apply` only when you intend to scale the existing local Compose workers. A one-shot first observation normally holds; `--watch --apply` allows sustained observations to apply bounded changes. The command uses `--no-build --no-deps --pull never`, verifies existing per-worker limits of one CPU and 768/1024/768 MiB, and leaves PostgreSQL, object storage, Temporal, and API alone. Stop with Ctrl-C. It does not resize individual workers.

`CAPACITY_CPU_BUDGET` (default 9) and `CAPACITY_MEMORY_MIB_BUDGET` (default 8192) are explicit budgets for workers combined. Reserve additional host capacity for the shared services before setting them. `CAPACITY_INTERVAL_SECONDS` accepts 15–60. Live extraction growth requires `MODEL_MAX_CONCURRENT_REQUESTS`; proposed extraction activity slots must fit that user-supplied provider limit. Recent observed 429/throttling signals hold extraction growth. An unknown live quota always holds extraction, and this tool cannot infer provider request/token quotas or prove that a provider permits a higher replica count.

The live quota guard applies if the controller has `MODE=live`, a configured `MODEL_API_KEY`, or any live application without a committed final audit in PostgreSQL. Each observation checks live application mode independently from review-age and throttle summaries. If that mode observation is unavailable or malformed, the controller requires a live quota. This also protects a fixture-configured controller when a separately started live API submits work. Reports show only credential presence, configured mode and the observed active live count; they never include the key. Report `mode` describes the effective quota constraint, not the mode of every sampled execution. Fixture-only growth is allowed only with a fixture controller, no configured model key, and a confirmed zero active live applications.

Statistics use the pinned SDK's actual enhanced `DescribeTaskQueue` API and fall back to the current per-type default statistics. Unsupported statistics are labeled unavailable, never invented. Workflow sticky queues and eager dispatch make queue statistics approximate. Retry/throttling diagnostics sample up to ten recent histories per queue plus available audit summaries; not every provider attempt is visible in history. Active activity counts inspect up to 500 running executions. Human review age is reported for operators, and waiting reviews do not trigger activity scale-up. Fixture measurements do not establish live model throughput or unlimited scaling.
